这张表是迭代顺序，不是把旧版全部目标重新设成发布前置条件。每次选取一个能够交付的改进，冻结本版支持范围；同类工作根据实际进展调整到后续版本。需要独立入口的新能力可以与已有稳定入口并存。

## 每版怎样完成

1. 确定本版新增功能、使用方式和支持边界，复用已经完成的实现与证据。
2. 完成新增及受影响部分的测试；涉及数据库行为时，运行对应的真实数据库场景。未执行项如实记录。
3. 检查旧接口、预算和证据重放的兼容性。复杂的语义改动安排独立复核，不为文档或打包调整重复全部历史实验。
4. 生成源码与便携包，使用新目录安装和运行示例；发布到 GitHub、Mooncakes 后核对公开包及新消费者。
5. 发布说明介绍新增功能、用法、兼容性和已知边界，详细实验和开发过程通过链接提供。

不支持的语句、未知提交、缺失来源和计算预算耗尽继续返回明确的覆盖缺口或无法判定。`oneMinimal`、完整结果集和版本来源仍按各自契约解释。缩小发布范围不改变判断规则，也不把推断写回原始观察。

## 性能优化贯穿升级

优先减少采集重复编码和额外写入，再处理图索引、报告中间分配与搜索状态分配。每项优化选择与改动相关的固定负载，同机、同工具链、同输入和同输出范围比较；报告真实收益和回退情况。没有性能改动的发布，不必重新执行整套正式测量。

此前的图组提速 1.3 倍、RSS 比 0.8、困难搜索与 512 事务缩减提速 1.5 倍，以及完整采集 C/A 吞吐 0.90、P95 比 1.15，继续作为优化方向，不再要求每个小版本全部达到。正式对比继续沿用保留原始样本的测量方法；缩小输出、改变输入或混合不同实现的结果，不能计作同口径提速。

完整采集成本仍区分 A 原业务、B 开启来源但关闭事件采集、C 完整来源和持久化。后续分别测量低并发、多连接、热点和 CRUD/负读负载；数据不足时只公布已完成的负载结果。

## 持续增强清单

- 普通表：条件 UPSERT、owner 更新、主/心跳/清理/重连的更广覆盖，来源闭包和安全保留。
- ORM：连接池复用、同步/异步、保存点、提交后断连及新事务重试。
- 分类与对照：六种明确模型定义、类别专用搜索，以及已冻结的寄存器/列表原始历史对照。
- 排障：dislock、ORM 和 MLflow 组件的更多真实并发回归及成本记录。
- 规模：按实际验证逐步扩展图、操作和边数量；图容量与精确枚举容量分别说明。
