# SELECT returned-row constraints: revision2 candidate

This revision fixes two independently observed scope holes in the first source mapping prototype: a WHERE key binding of18 was accepted with a returned id17 row, and two identical returned primary keys were accepted as an initial-row mapping. The first22-file freeze, its runtime, author56 checks, independent50 checks and original probe receipts remain unchanged.

The new mapper independently checks configured WHERE AND conditions against actual delivered native fields and verifies unique returned primary keys for the supported single-table SELECT. Parameter values come from the existing independent MoonBit SQL/binding result; producer AST status and supplied reports do not authorize them. Integer comparisons use exact signed int64 lexemes; text uses the existing Unicode/codepoint comparator underlying UTF8 C order. No source lookup supplies a missing business column.

The old native/fetch consistency result is retained as `nativeDeliveryCheck`. The `fetch` field now has an independent format `moontxnwitness-select-returned-row-constraints/v4`, semantic `configured-WHERE-AND-and-primary-key-returned-rows/v4-2`, algorithm `independent-returned-row-predicate-and-key-2` and counter `select-returned-row-constraint-counters/v4-2`. This avoids presenting a native-byte-only v1 result as SELECT predicate verification. Wrong returned values and duplicate PKs produce `fetch.valid=false` with the original result identity and row-index/typed-value witness. These are capture/contract contradictions, not inferred database isolation anomalies.

The root mapping uses semantic `original-select-initial-source-and-returned-constraints/v4-2`, algorithm `independent-native-initial-row-and-predicate-join-2`, and counter `source-fetch-mapping-step-counters/v4-2`. Caller budgets remain independent of reports. The original profile1 runtime stays preserved by its original freeze; profile1 report bytes are not silently interpreted as profile2.

Missing predicate/PK columns, an unexhausted fetch prefix, unsupported cursor movement or unverified ordering preserve explicit gaps. A reliable false condition or duplicate PK wins over an unrelated missing column or incomplete prefix when already observed within budget. Repeated fetch starts continue to be rejected by the existing native-delivery verifier.

A legal exhausted empty result may satisfy returned-row constraints vacuously, but `resultSetCompletenessVerified` and `negativeReadSourceVerified` remain false. A partial business projection may satisfy returned constraints if every condition and PK field was actually delivered; the overall source mapping still refuses to fill omitted business values and remains `row-projection-incomplete`. ORDER BY validation is outside this minimal profile and produces an explicit gap.
