## 能够判断与仍不能判断的部分

预备输入上的阶段测量，其 P95 差分别为：解析 -0.335 毫秒、依赖推断 +0.721 毫秒、纯缩减 -0.007 毫秒。纯缩减阶段没有复现全流程的尾部差异。

全流程还包含原始输入解析、最终完整 JSON 生成及客户端 JSON 解码。各阶段是独立测量，不能相加推出端到端成本，也不能根据纯缩减阶段相近就排除全流程中的分配与 GC 交互。完整输出均为 122,250 字节；省略来源或改成摘要不属于解决方法。

静态核对固定公开 v0.1.0 主 core 为 675,320 字节，当前主 core 为 675,397 字节。对生成符号与临时变量做一致的 alpha 重命名后，编译 JS 剩余正文差异为引擎版本文字和重放兼容版本允许表，未见热路径算法或分配表达式的新增变化。审阅差异另存为 `performance-v010-formal-2026-10-20T10-32-08-052Z-compiled-alpha.diff`。这是文本审阅线索，不是 JavaScript AST 等价证明，更不是性能通过的替代条件。

两轮没有采集 GC 事件、暂停时间、分配速率、每批 CPU 时间/频率或后台调度数据。RSS 峰值接近不能证明分配率相同或没有 GC 暂停。虽然测量前已暂停已知本地重型任务，仍不能根据现有记录确认或排除操作系统干扰。因此，当前结论为：**根因尚未证实**，不能直接写成“GC 导致”或“只是环境噪声”。

## 后续诊断边界

不再为了取得通过结果而重复原流程。若继续诊断，应先冻结专门的诊断协议，再针对 reduction-512 采集 GC 事件、CPU 时间及堆使用变化，并将慢样本与这些时间线关联；双方使用同样的诊断开销和预先固定的平衡顺序。诊断数据与正式验收分别保存。

另外拆分检查完整 JSON 生成和客户端解码，确认慢尾部发生在哪个环节。只有证据指向具体分配或计算成本后再优化；之后按原有完整门槛检查新代码，失败记录仍不覆盖。

本次性能脚本直接加载主分析 core，没有加载独立 capture core，也没有测量同步 SDK 的双模块启动或实际数据库采集开销。主 core 相对第一版单模块缩小的静态体积收益，不等同于整个 SDK 的体积、启动或运行性能收益。PostgreSQL 采集成本需使用自己的业务开关实验报告。
