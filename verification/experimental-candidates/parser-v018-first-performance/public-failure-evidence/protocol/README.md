# ASCII解析候选正式对照协议（仅准备，尚未测量）

对照对象是原实际15 core `a42c29e0ffcb516d6b6cd84ee273d50aa99ad6c989ad4d3e6f97d6c433ec0cef` 与隔离候选重新编译的15 core `5d5d87c2b9c283822d32a343e406d687e2c3944a15adc32dd6ceaf5391531b8e`。不导入主线16/17，不构建、不安装、不联网、不运行数据库。候选没有变成正式18；这里尚无速度、P95或RSS结果。

协议固定为每个输入、每个阶段、每个引擎 **5次预热、30次样本、3批独立进程**；每批交替before/after顺序。阶段为完整balanced JSON-in/JSON-out和只解析。冷启动用另一个新进程执行一次，不混入30次热样本。程序记录每批及合并90样本的中位数、nearest-rank P95、输入/输出字节、进程峰值RSS及采样RSS、导入耗时、首调用耗时和外部冷进程墙钟时间。

测量前先用独立进程保存并逐字节比较完整输出；每次样本计时结束后仍核验完整输出SHA。不删除引擎版本、算法、预算、统计或业务字段。解析阶段输出是完整公开typed History字段：Map全部逻辑键值按键排序，数组顺序/Int64/None类型保持；运行时私有随机桶布局不视作公开History。完整分析阶段直接比较原输出字符串字节。验证器开销在计时外，峰值RSS仍包括同一进程的核验/序列化，不能称为纯解析分配量。

输入包含3份现有固定v010基线负载，以及合法的known ASCII、custom ASCII、转义ASCII、Unicode解析重负载。所有输入先封SHA，不能看测量结果后更换。控制负载的median和P95热延迟回退阈值均为 `max(基线×10%, 2ms)`，冷进程墙钟median也按同阈值独立列出；RSS只记录，不预先许诺降幅。正确性、协议是否完成、控制回退是否通过分别报告，不把“差异在容许范围”说成提速。

大临时输出只写根授权指定的D盘scratch，新进程、日志、完整输出与首失败均保留，不自动重试或删失败。C盘只存本轻量准备代码/固定输入以及最终小收据。三个独立批次并不证明消除了温度、后台任务或机器状态影响；主机独占依赖根的显式授权和声明。

只有根另给独占授权JSON与其SHA后才可执行：

```text
python -B artifacts/v018-performance-preparation/run-protocol.py --authorization AUTH.json --authorization-sha256 ROOT_SUPPLIED_SHA256
```

模板中的false和空SHA使其不可执行。准备阶段没有调用worker，没有导入任何core，没有计时或读RSS，也没有提前声明优化收益。
