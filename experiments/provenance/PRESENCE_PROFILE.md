# Fixed-key CRUD and absence experiment

This is an opt-in v0.1.2 experiment, not a stable adapter or support for arbitrary
SQL. It installs a version column, transactional state/audit tables, one owned
BEFORE trigger and two owned VOLATILE helpers inside a new, explicitly controlled
`mtw_provenance_*` schema. Those installation changes are material: writes to keys
outside the frozen universe and non-null primary-key changes are rejected by the
installed trigger. This is not a promise of unchanged behavior for arbitrary SQL.

The application templates are generated by `PresencePointProfile`:

```python
from presence_profile import PresenceCapture, PresencePointProfile

profile = PresencePointProfile("mtw_provenance_my_fixture", "items")
capture = PresenceCapture(profile, keys=("a", "b", "never"), exclusive_writers=True)
capture.initialize(dedicated_idle_autocommit_setup_connection)
# Do not start workers before initialize returns with commit acknowledged.
connection = capture.wrap(business_connection)
assert connection.execute(profile.read_sql, ("never",)).fetchone() is None
connection.execute(profile.insert_sql, ("never", "created"))
connection.execute(profile.update_sql, ("same-value", "never"))
connection.execute(profile.delete_sql, ("never",))
connection.commit()
capture.close()
trace = capture.document()  # experimental traceSchema: 2
capture.uninstall(dedicated_idle_autocommit_setup_connection)
```

Import this experiment from `experiments/provenance/`. PostgreSQL 18 and psycopg 3
with standard synchronous tuple cursors are required. The business table has
exactly two original columns, in declared order: one text primary key and one
text value, without defaults, identities or generated columns. The value may be
nullable. Extra business columns, RLS, inheritance, incoming/outgoing foreign
keys, rewrite rules, user triggers, CHECK/EXCLUDE constraints and expression or
partial business indexes are rejected. Deferred primary/unique constraints and
non-native btree operator classes are also rejected: an added helper must not
turn a deferred uniqueness failure into an earlier missing-audit failure.
Setup, source/OID/nonce/DDL verification,
and the actual initial snapshot share one locked installation transaction.
Absence is initialized only for caller-declared missing keys. Existing keys
must all be included; the universe never expands implicitly.

## Version sources

State contains every initialized key, including absent keys. Before a successful
INSERT/UPDATE/DELETE, the owned trigger locks that key's state and creates a fresh
UUID audit version in the same business transaction. The audit retains the
exact predecessor, presence transition and old/new business payload. A unique
partial predecessor index prevents a committed chain from forking. UUIDs are
identities; neither their sort order nor clocks nor transaction IDs establish
commit order.

UPDATE returns its actual OLD/NEW tokens. DELETE returns OLD plus a separate
tombstone obtained by the owned `delete_token(key, OLD.token)` function. That
VOLATILE function looks only for exactly one immutable DELETE audit row with
that key and predecessor. It never obtains a deletion token from mutable current
state. INSERT returns NEW plus its exact immutable insertion predecessor.
The actual PG fixture must prove that these same-statement helpers see their
own BEFORE-trigger writes. Static or fake-driver success does not prove it.

A point SELECT joins the business row and state in one MVCC statement. It checks
that both presence and live token agree, so it never combines an earlier business
read with a later state query. The server's hidden helper row is buffered. The
business cursor still exposes its original zero/one row, one-column description,
rowcount, status message and row position. A positive read is recorded when the
application receives its row. A negative read is recorded only when the
application actually receives EOF; merely executing SELECT records no read.
An unconsumed result is a coverage gap. `arraysize=0` consumes nothing and does
not establish EOF. Negative fetch sizes are outside the observer contract and
produce a gap while retaining the pending observation.

Original INSERT/UPDATE/DELETE have no RETURNING. Added server metadata results
are hidden; fetch retains the pinned driver's no-records ProgrammingError
contract. Real driver execution errors are re-raised as the same exception object.
NULL primary keys are left to the original NOT NULL constraint; duplicate live
keys are left to the original uniqueness constraint. If an original NOT NULL
value constraint fails after the BEFORE trigger, PostgreSQL must roll back all
its metadata changes with that statement. The fixture compares these behaviors.

## Trace and projection contract

The stable schema-1 normalizer must reject this schema. The independent
`normalizePresenceCapture` experimental entry point validates these additional
facts before producing a register history:

```text
traceSchema: 2
presenceFacts: {
  schema: 1,
  projection: "column-presence-register-v0.1.2-experimental",
  initial: [{ key, version, present }],
  reads: [{ seq, tx, key, version, present }],
  writes: [{ seq, tx, key, version, predecessor,
             oldPresent, newPresent, action: "insert" | "update" | "delete" }]
}
```

Keys use the stable typed `Table.key` representation. Initial facts exactly cover
the locked snapshot. The old snapshot map binds each initial key and token; its
presence boolean is a new raw fact checked against later transition/read facts.
The old map cannot authenticate that boolean for an otherwise unused key.
Every read/write fact refers to the original corresponding
operation event by sequence number, transaction, key and version. Metadata
predecessors **are not application reads**. DML emits write operations only;
positive/negative SELECT delivery emits read operations. In particular a
predecessor cannot be used to invent an application read of an old business value.
The MoonBit validator independently checks all operation/fact bindings, presence
transitions, complete source chains, intermediate writes and aborted transaction
semantics before exporting factual committed version orders. Missing or
inconsistent facts must export no complete history.

Initial/read/write facts share the recorder's retained byte/node budget. Reads
and writes together have a 10,000-fact limit. If an operation event is omitted by
the event/session budget, no orphan fact is synthesized from a guessed sequence.
Exhaustion produces a coverage gap, not a complete conclusion. Default recorder
limits still include 65,536 events, 512 KiB per event, 8 MiB / 262,144 retained
nodes, and bounded raw parameter/result trees. These are evidence limits, not a
bound on application buffers or process RSS. A document copy may transiently
duplicate bounded retained evidence. This experiment rejects `jsonl_path`: the
stable JSONL header/loader describes schema 1, so complete schema-2 documents are
written by the fixture instead of mislabeling a log as schema-1 compatible.

Unknown statements execute their original text and create a coverage gap. Zero-row
UPDATE/DELETE have their original business result, but do not invent an absence
read or a write. UPSERT, original RETURNING, savepoints, arbitrary conditional or
multi-row DML, async/server/custom-row cursors, dynamic key discovery and
automatic SQL parsing are unsupported. A trusted deployment must preserve the
owned DDL and route every writer through the declared capture window; this is
not continuous protection against a database administrator.

## Verification commands and evidence boundary

Run pure tests with the repository's optional driver environment:

```powershell
& .\artifacts\pg-driver\Scripts\python.exe -B -m unittest discover -s experiments/provenance -p test_presence_profile.py -v
```

Only against a caller-controlled database, with `MTW_PG_CONNECTION_FILE` pointing
to a private connection JSON or `MTW_PG_DSN` set privately:

```text
node experiments/provenance/presence_e2e.mjs --schema mtw_provenance_presence_unique --output verification/presence-unique
```

`MTW_PYTHON` can select the interpreter. The requested schema and output directory
must be new. The fixture creates and normally removes its schema; it never
adopts an existing schema. Missing database configuration exits as not executed.
`--keep-schema` explicitly retains the newly created test schema for inspection.

The fixture contains six scenarios: serial CRUD/repeated value/negative read/
delete-reinsert/whole-transaction rollback; negative-point write skew; a real
READ COMMITTED row-lock wait followed by DELETE and reinsertion; unread negative
results; unknown SQL/savepoints; and zero-row/NULL-key coverage gaps. Eight
installation alterations/failures exercise strict owned DDL and atomic rollback;
two additional schema rejections cover deferred primary keys and INSERT defaults.
The wait must be confirmed through `pg_blocking_pids`, not elapsed sleeps. Raw
audit, polling protocol, trace, coverage, history, report, capsule and reduction
artifacts are retained and bound by SHA-256/size in the receipt. Source hashes
are captured before execution and checked afterward. These hashes detect
artifact mismatches; they do not authenticate collection, prove application
adoption or complete v3 packaging.

Current evidence is deliberately staged. The 22 Python fake-driver checks pass.
The first actual PG18.6 / psycopg 3.3.6 raw run passed all six scenarios and its
then-eight installation rejections:
`verification/provenance-presence/run-dac8a13a07b34679a5c5635ad0097196/presence-database.json`.
It confirmed same-statement VOLATILE helper visibility, complete metadata
rollback, original 23502/23505 errors and the READ COMMITTED lock-wait source.
That receipt remains `driver-passed-core-pending`; it does not certify the later
additional schema rejection assertions or MoonBit projection/capsules. Its owned
cluster was shut down and retained as `run-kro9350v` in the selected D-drive
work root. No performance, production-deployment or external-application result
is claimed. This new capability does not close the separate v0.1.1
full-application or v0.1.7 real-defect acceptance gates.
